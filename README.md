# Financial Management System Prototype — Laravel + MySQL Backend

This is the database/backend/security layer built around the existing
Financial Management System frontend prototype. It does not replace or
redesign that frontend — see `docs/ARCHITECTURE_ASSESSMENT.md` for exactly
what was inspected before this was built, and
`../fms/` (the original delivered prototype) for the untouched HTML/CSS
reference.

## What this project is

A standard Laravel 11 application skeleton **plus** the app-specific code
in this delivery:

```
app/Models/            16 Eloquent models
app/Http/Controllers/  Auth/ (login, password) + Api/ (every module)
app/Http/Middleware/   EnsurePermission, EnsureAccountActive
app/Http/Requests/     Server-side validation per module
app/Services/          Transactional business logic (the ACID-critical part)
app/Policies/          UserPolicy (last-administrator safeguard)
database/migrations/   20 migrations, run in order, from a clean DB
database/seeders/      Roles, permissions, departments, 4 demo users
routes/web.php         Login/logout/password routes
routes/api.php         Every module's JSON API, permission-gated
resources/views/auth/  Real login / forgot-password / reset-password views
docs/                  Architecture assessment, DB architecture, security
```

This repository intentionally does **not** include the rest of a full
Laravel skeleton (`vendor/`, `bootstrap/cache/`, `storage/`,
`public/index.php`, `composer.json` lock file, `artisan`, etc.) — those
are generated by `composer create-project laravel/laravel` in step 1
below and are identical for every Laravel project regardless of what it
does, so reproducing them here would just be noise. Everything above is
what's specific to this system.

## Installation (local XAMPP development)

1. **Create the base Laravel app**, then copy this delivery's `app/`,
   `database/`, `routes/`, `resources/views/auth/`, `bootstrap/app.php`,
   and `.env.example` into it, overwriting the generated defaults:

    ```bash
    composer create-project laravel/laravel fms-app
    cd fms-app
    # copy this delivery's folders in on top, per the list above
    composer require laravel/sanctum
    php artisan install:api   # publishes Sanctum config if not already present
    ```

2. **Copy the existing static frontend** into `public/app/` so it is
   served as plain static files, side by side with Laravel's own
   `public/index.php`:

    ```bash
    mkdir -p public/app
    cp -r ../fms/css ../fms/js ../fms/pages ../fms/index.html public/app/
    ```

    The frontend's relative paths (`../css/style.css`, `../js/data.js`
    from inside `pages/*.html`) work unchanged no matter where the
    `css/js/pages` trio is mounted, so no path rewriting is needed here.

3. **Configure the database**:

    ```bash
    cp .env.example .env
    php artisan key:generate
    # edit .env: DB_DATABASE, DB_USERNAME, DB_PASSWORD, DEMO_USER_PASSWORD
    ```

    In phpMyAdmin (bundled with XAMPP) or the `mysql` CLI, create the
    database named in `.env` (`fms_database` by default) — Laravel's
    migrator does not create the database itself, only its tables.

4. **Run migrations and seeders**:

    ```bash
    php artisan migrate
    php artisan db:seed
    ```

    `db:seed` runs `RolePermissionSeeder → DepartmentSeeder → UserSeeder`
    in that order (see `database/seeders/DatabaseSeeder.php`) because
    users reference both roles and departments. If you ever need to start
    over from a clean schema: `php artisan migrate:fresh --seed`.

5. **Serve the app**:

    ```bash
    php artisan serve
    ```

    Visit `http://127.0.0.1:8000/` — it redirects to `/login`. Sign in
    with one of the seeded demo accounts (Section 68):

    | Role                  | Email                       | Password                                     |
    | --------------------- | --------------------------- | -------------------------------------------- |
    | Administrator         | `admin@example.test`        | value of `DEMO_USER_PASSWORD` in your `.env` |
    | Accountant            | `accountant@example.test`   | same                                         |
    | College Administrator | `collegeadmin@example.test` | same                                         |
    | Employee              | `employee@example.test`     | same                                         |

    These are clearly-fictional `.test` addresses (an IANA-reserved,
    non-resolving TLD), never real production credentials.

## Registering middleware on Laravel 10 (if not using the Laravel 11 skeleton)

`bootstrap/app.php` in this delivery assumes a Laravel 11 skeleton. If
your `composer create-project` produced a Laravel 10 app instead (i.e.
you have `app/Http/Kernel.php`), register the two custom middleware
there instead:

```php
// app/Http/Kernel.php
protected $middlewareAliases = [
    // ...existing entries...
    'permission' => \App\Http\Middleware\EnsurePermission::class,
    'account.active' => \App\Http\Middleware\EnsureAccountActive::class,
];
```

and delete the `->withMiddleware(...)` block from `bootstrap/app.php`
(Laravel 10 does not use that file for routing/middleware configuration).

## Frontend integration status

Complete. `js/data.js` is now an async API client (fetch-based, session-
cookie authenticated via Sanctum) instead of a localStorage store, and
every per-module script (`js/budget.js`, `js/revenue.js`, `js/expenses.js`,
`js/payable.js`, `js/receivable.js`, `js/funds.js`, `js/procurement.js`,
`js/assets.js`, `js/reports.js`, `js/audit.js`, `js/dashboard.js`,
`js/navigation.js`) has been converted to `async`/`await` against it.
`js/auth.js` no longer contains a hardcoded `ROLES` object or a
`loginAs()` shortcut — it calls `GET /api/me` once per page load and
caches the role/permission set for that page's lifetime. The old
role-picker `index.html` has been replaced with a small redirect stub to
the real `/login` page. Button-level visibility (Edit/Delete/Approve/etc.)
now checks `userCan('<permission_slug>')` against that cached set instead
of the old `role.canEditFinancials`-style booleans — cosmetic only, since
every one of those actions is re-checked server-side by
`permission:<slug>` middleware regardless of what the button shows.

## Sanctum configuration (session-based SPA auth for the static frontend)

Because the existing frontend is plain static HTML/JS served from
`public/app/`, it authenticates against the API the same way a Sanctum
SPA does: same-origin session cookie, no API tokens. Two settings need to
match your local URL after `composer require laravel/sanctum`:

```env
# .env
SANCTUM_STATEFUL_DOMAINS=127.0.0.1:8000,localhost:8000
SESSION_DOMAIN=127.0.0.1
```

```php
// config/sanctum.php — 'stateful' array must include the host/port you
// actually browse to, or /api/* requests will be treated as unauthenticated
// token requests instead of session requests and every call will 401.
```

`js/api-client.js` calls `GET /sanctum/csrf-cookie` once before the first
mutating request in a page load, which is what lets the browser's
`fetch()` calls carry a valid `X-XSRF-TOKEN` header automatically.

## Testing

```bash
php artisan test
```

- `tests/Feature/AuthenticationTest.php` — valid/invalid login, rate
  limiting, disabled-account rejection, logout invalidating the session.
- `tests/Feature/AuthorizationTest.php` — an Employee gets 403 on
  Administrator/Accountant-only endpoints; an Accountant succeeds on the
  same ones.
- `tests/Feature/FundAllocationTest.php` — the concurrent-allocation race
  condition from Section 51, asserting the second over-allocating request
  is rejected rather than both succeeding.

See `docs/SECURITY_ARCHITECTURE.md` and `docs/DATABASE_ARCHITECTURE.md`
for the full authentication/authorization flow and schema reference,
and `docs/ARCHITECTURE_ASSESSMENT.md` for the Phase 1 inspection this
entire design was derived from.
